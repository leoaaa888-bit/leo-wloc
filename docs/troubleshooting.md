# 排查

按现象找。每一节都从「最可能」排到「最不可能」。

---

## 选点页面显示红色「模块没有生效」

写入请求没被模块拦下来。**九成是证书信任那一步。**

1. **代理连着吗** — 状态栏有没有 VPN 图标? Safari 的流量必须走代理。
2. **模块启用了吗** — 在代理工具里确认 Leo WLOC 模块开关是打开的, 不只是「已下载」。
3. **MITM 开了吗** — 代理工具的 MITM 总开关。
4. **证书装了并且"完全信任"了吗** — 这是最常漏的一步:

   `iOS 设置 → 通用 → 关于本机 → 证书信任设置` → 找到你的代理工具的 CA →
   把开关打开

   只在「VPN 与设备管理」里装了描述文件是**不够的**, 必须再到「证书信任设置」里
   打开完全信任。

5. **MITM 主机名包含 `gs-loc.apple.com` 吗** — 模块自带了, 但如果你手动改过配置,
   或者别的模块覆盖了 hostname, 就可能丢。
6. **别的模块抢了同一条规则吗** — 如果你装过其它 WLOC / 定位类模块, 先全部关掉。

验证方法: 在代理工具的日志里搜 `wloc-settings`, 看这条请求有没有被脚本处理。

## 储存成功 (看到 ✓) 但定位没变

### 先看系统版本

- **iOS 27 beta 6 及以后 —— 本项目无法工作。** 见 [系统兼容性](compatibility.md)。
- **iOS 26.x —— 需要重启设备。**

### iOS 26+ 的定位缓存

Apple 从 iOS 26 起把真实定位结果长时间留在 `locationd` 内存里复用。脚本日志显示
「已改写」而位置不动, 基本都是这个。

**只有重启能清掉。** 飞行模式、关闭定位服务、杀 App、切网络**都不行**。

成功率最高的顺序:

1. 先储存好坐标
2. 开飞行模式 → 关闭定位服务 → **重启**
3. 关飞行模式 (WiFi 也保持关) → 连上代理, 确认 VPN 图标 → 打开定位服务
4. 打开地图验证

### GPS 压过了网络定位

本项目**只改网络定位**。户外 GPS 信号好的时候, 系统会优先信 GPS。

室内、或者把 WiFi 关掉只留蜂窝, 效果最明显。

### 脚本没拿到二进制 body

打开 `logLevel=debug`, 如果日志里出现:

```
[Leo WLOC][W] 无二进制 body, 跳过 (模块是否缺少 binary-body-mode?)
```

说明模块规则里的 `binary-body-mode` 丢了。用订阅的模块不会有这问题, 手动改过配置的
检查一下这个参数。

## 日志里出现「未找到可改写的 wloc 载荷」

脚本拿到了 body, 但没能在里面认出 WLOC 结构。

可能原因:

1. **响应被压缩且不是 gzip** — 脚本认 gzip (`1f 8b` 魔数)。如果代理工具透传的是
   br (Brotli), 脚本解不开。多数工具会替你解掉 Content-Encoding, 出现这种情况可以在
   模块里给请求加 `Accept-Encoding: gzip`。
2. **Apple 改了响应格式** — 帧结构是逆向来的。脚本已经有两层兜底 (逐偏移试帧头 +
   裸 protobuf 扫描), 都失败说明格式确实变了。
3. **拦到的不是 WLOC 请求** — 检查匹配的 URL 是不是真的 `/clls/wloc`。

**注意: 这种情况下脚本会原样放行响应**, 不会返回半成品。定位保持真实, 不会坏掉。

## 想确认脚本到底在干什么

把 `logLevel` 改成 `debug` 或 `all` (Surge/Loon/Stash/Shadowrocket 在模块参数里改)。

正常工作时的日志长这样:

```
[Leo WLOC][D] Leo WLOC v1.0.0 on Shadowrocket
[Leo WLOC] 使用已保存坐标: 114.159437,22.284774
[Leo WLOC][D] input length=2847 gzip=false
[Leo WLOC] 已改写 offset=2 locations=12 wifi=11 cell=1 skipped=0
[Leo WLOC] 目标坐标 114.159437,22.284774 精度=25m 扰动=0.0m 改写点位=12
```

透传时:

```
[Leo WLOC] 透传模式: 无持久化坐标且模块参数为出厂示例值, 不修改定位
[Leo WLOC] 透传模式: 未设置坐标, 原样放行 (恢复真实定位)
```

QX 用户看不到模块参数, 但可以在选点页面 URL 后加 `?logLevel=debug` 影响
`wloc-settings.js` 的日志 (不影响 `wloc.js`)。

## 粘贴链接解析失败

| 报错 | 含义 |
| --- | --- |
| `未能从链接中解析出经纬度` | 这条链接里没有可提取的坐标。换一种分享方式 (选「共享地点」而不是「共享导航」), 或直接复制坐标文本。 |
| `百度这条链接的坐标要靠网页脚本才能取到…` | 百度港澳台 POI 的已知限制。按提示在浏览器打开链接, 等地址栏变成 `map.baidu.com/poi/名称/@数字,数字,19z` 再复制整条地址。 |
| `解析出的坐标超出合法范围` | 通常是 `cs=` 参数指定了错误的坐标系。去掉它, 让接口按来源自动判断。 |
| `解析服务不可达` | 你的 Pages / Worker 没部署好, 或者网络到不了。 |

## 解析出来的位置偏了几百米

这是坐标系没对上。各家的规则:

| 来源 | 中国大陆 | 港澳台 |
| --- | --- | --- |
| 苹果地图 / Google | GCJ-02, 需换算 | **WGS84, 不换算** |
| 高德 / 百度 | GCJ-02 / BD-09, 需换算 | 同左, **仍需换算** |

接口会按「来源 × 地区」自动分派。如果你觉得它判错了:

- 强制按 GCJ-02 换算: `&cs=gcj`
- 强制按 BD-09 换算: `&cs=bd`
- 完全不换算: `&cs=none`

深港边界一带 (罗湖 / 落马洲 / 沙头角 口岸两侧约 1 公里内) 可能判错 —— 那些地方本身
就骑在边界上。遇到了用 `cs=` 手动指定。

## 在高德底图上选的点, 换成卫星底图就偏了

不会。页面内部**恒以 WGS84 为准**, 切到高德底图时会做双向换算 (深圳一带约 600 米)。
如果你确实看到针脚跳动, 那是换算在起作用 —— 底图画的是 GCJ-02 地物, 同一个 WGS84
坐标在两张底图上本来就对应不同的像素位置。

存进设备的始终是 WGS84 值, 与你在哪张底图上选的无关。

---

## 换了设备 / 重装了代理工具, 收藏没了

收藏列表存在**浏览器 localStorage**, 换浏览器或清缓存就没了。

**生效坐标**存在代理工具的持久化存储 (`wloc_settings`), 两者是独立的。收藏丢了不影响
已经写进设备的坐标。
